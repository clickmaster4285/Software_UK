# **SECTION 02 — DEFINITION**

## **What Are Technical Support Services?**

Technical support services help businesses investigate, diagnose and resolve technical problems affecting software applications and related workflows.

The purpose is to determine:

* What has gone wrong  
* Which part of the software is affected  
* What caused the problem  
* How widely the issue affects the application  
* Whether configuration, integration or software changes are required  
* Whether the problem needs escalation into maintenance or development work

A typical support workflow can look like:

**Technical Issue**  
 → **Issue Review**  
 → **Diagnosis**  
 → **Troubleshooting**  
 → **Resolution / Escalation**  
 → **Verification**  
 → **Documentation**

Technical support is therefore focused on **problem identification and resolution**, rather than simply performing general ongoing software development.

# **SECTION 03 — SPECIFIC CAPABILITIES**

## **Our Technical Support Services**

### **Application Technical Support**

Support existing software applications where technical problems affect users, workflows or connected functionality.

Application support can involve:

* Investigating application errors  
* Reviewing unexpected behaviour  
* Troubleshooting failed functionality  
* Examining user-reported issues  
* Reviewing application logs  
* Identifying integration problems  
* Investigating backend issues  
* Investigating frontend issues  
* Verifying resolved problems

The appropriate support process depends on the application architecture and nature of the reported problem.

### **Software Troubleshooting**

Troubleshooting involves systematically narrowing down the possible causes of a technical problem.

A typical workflow can follow:

**Reported Problem**  
 → **Reproduce Issue**  
 → **Review Technical Evidence**  
 → **Isolate Cause**  
 → **Determine Resolution**  
 → **Verify Result**

Troubleshooting can involve software behaviour, integrations, application configuration, data flows or other connected components.

### **Technical Issue Diagnosis**

The visible symptom is not always the actual cause of a software problem.

Technical diagnosis can consider:

* Application errors  
* Logs  
* API responses  
* Database behaviour  
* Integration failures  
* Configuration  
* User actions  
* Recent software changes  
* Environment differences  
* Reproducibility

The aim is to identify the source of the problem before deciding what corrective work is appropriate.

### **Incident Support**

Production software can occasionally experience issues that affect normal application operation.

Incident support can involve:

* Recording the issue  
* Assessing impact  
* Gathering technical information  
* Investigating the cause  
* Identifying a workaround where appropriate  
* Escalating software defects  
* Verifying restoration  
* Documenting findings

The required process depends on the severity and business impact of the incident.

### **Production Application Support**

Applications operating in production may require technical assistance when unexpected behaviour occurs.

Support can include investigation around:

* Application failures  
* Failed transactions or workflows  
* API problems  
* Authentication issues  
* Integration failures  
* Data-processing problems  
* Application errors  
* Unexpected output

Production support should be based on the actual architecture and available technical information.

# **SECTION 04 — HOW IT WORKS**

## **How Technical Support Works**

Technical support begins by collecting enough information to understand and reproduce the problem.

A typical support lifecycle can look like:

**Issue Reported**  
 → **Information Collection**  
 → **Reproduction**  
 → **Technical Investigation**  
 → **Root-Cause Identification**  
 → **Resolution / Escalation**  
 → **Testing**  
 → **Closure**

### **Issue Reporting**

Useful information can include:

* What happened  
* Expected behaviour  
* Actual behaviour  
* Affected functionality  
* Error messages  
* Screenshots where relevant  
* Time of occurrence  
* User actions  
* Environment  
* Whether the problem can be reproduced

Clear issue information helps narrow the investigation.

### **Issue Reproduction**

Where possible, reproducing the problem can help determine:

* Which conditions trigger it  
* Whether it affects all users  
* Whether it is environment-specific  
* Which software component is involved  
* Whether recent changes are related

### **Technical Investigation**

Investigation can involve reviewing relevant application components such as:

* Source code  
* Application logs  
* APIs  
* Databases  
* Integrations  
* Application configuration  
* Deployment environment  
* Recent changes

### **Resolution or Escalation**

Some issues can be resolved through configuration or operational changes.

Others may reveal a code-level defect requiring software maintenance or development.

In those cases, the issue can move from:

**Technical Support**  
 → **Engineering Assessment**  
 → **Software Maintenance / Development**  
 → **Testing & Release**

# **SECTION 07 — ISSUE MANAGEMENT & ESCALATION**

## **Technical Support & Issue Escalation**

Not every software issue requires the same type of engineering response.

A useful escalation model can be:

**Reported Issue**  
 → **Initial Investigation**  
 → **Technical Diagnosis**

Then:

**Configuration / Operational Issue**  
 → **Technical Resolution**

or:

**Code-Level Defect**  
 → **Software Maintenance**

or:

**Larger Functional Requirement**  
 → **Software Development**

This distinction helps prevent routine technical support from becoming mixed with unrelated development work.

### **Issue Severity**

Issues can be assessed according to factors such as:

* Number of affected users  
* Business impact  
* Loss of functionality  
* Availability of a workaround  
* Technical risk  
* Data impact  
* Reproducibility

### **Escalation**

A problem may require deeper engineering when:

* A software defect is identified  
* Source-code changes are required  
* An integration requires redevelopment  
* Architecture changes are needed  
* Existing functionality requires modification

# **SECTION 09 — TECHNICAL SUPPORT VS MAINTENANCE**

## **Technical Support vs Software Maintenance**

These services work closely together, but their primary intent is different.

| Technical Support | Software Maintenance & Support |
| ----- | ----- |
| Investigates technical problems | Makes ongoing changes to software |
| Troubleshoots issues | Fixes code-level defects |
| Diagnoses causes | Updates software |
| Handles issue escalation | Improves maintainability |
| Supports production problems | Handles compatibility changes |
| Primarily problem-focused | Primarily engineering-focused |

For example:

**User Reports Application Failure**  
 → **Technical Support Investigates**  
 → **Software Defect Identified**  
 → **Maintenance Team Corrects Code**  
 → **Change Tested**  
 → **Application Updated**

## **Frequently Asked Questions About Technical Support Services**

### **What are technical support services?**

Technical support services help businesses investigate, diagnose and resolve technical problems affecting software applications and related workflows.

### **What does software technical support include?**

Software technical support can include issue investigation, application troubleshooting, technical diagnosis, integration support, incident investigation, escalation and resolution verification.

### **What is application technical support?**

Application technical support focuses on helping identify and resolve technical problems affecting an existing software application.

### **Can technical support troubleshoot software errors?**

Yes. Technical support can investigate software errors to identify the affected application area, likely cause and appropriate resolution or escalation path.

### **Can technical support help with API problems?**

Technical support can investigate API-related issues such as failed requests, authentication problems, unexpected responses and data-exchange errors.

### **Can technical support help with existing software?**

Yes. Existing applications can potentially be supported where sufficient access, technical information and software context are available for investigation.

### **What is the difference between technical support and software maintenance?**

Technical support primarily diagnoses and resolves technical problems, while software maintenance focuses on making ongoing changes, fixes and improvements to the software itself.

### **What happens if technical support finds a software bug?**

If investigation identifies a code-level defect, the issue can be escalated into software maintenance or development for correction, testing and release.

### **Can you support software developed by another company?**

Existing software can potentially be supported after the application, available documentation, technical environment and required access have been assessed.

### **Is technical support the same as IT help desk support?**

Not necessarily. This service focuses on technical support for software applications and related software workflows rather than general end-user hardware or broad IT help desk support.

### **Can technical support help with production applications?**

Technical support can investigate issues affecting production applications where appropriate technical access and information are available.

### **How much do technical support services cost?**

Cost depends on application complexity, issue type, investigation requirements, integrations, technical access and the amount of ongoing support required.

### **How long does it take to resolve a technical issue?**

Resolution time depends on the issue's complexity, reproducibility, application architecture, available technical information and whether software changes are required.
